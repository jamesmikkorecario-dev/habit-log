# ADR-0014: Managed backups and deletion-safe recovery

Status: implemented and locally verified for the authorized Deployment Remediation 2 on 2026-10-30; production provisioning and acceptance remain required. Extends ADR-0011's approved policy without changing immediate live deletion.

## Decision

Hosting is undecided. Use Laravel Artisan, existing PDO MySQL and PHP Sodium rather than assume a cloud provider, object store, database client executable or backup service. The managed workflow is opt-in through `RECOVERY_MODE=live`; default `off` preserves installations without configured managed backups. `off` is not an alternative admission path for a restored installation and must never be used to bypass failures. Deployment remains blocked until the operator enables and verifies the complete boundary or establishes a separately approved recovery solution.

Backups use an authenticated streaming format with Sodium secretstream XChaCha20-Poly1305. Records contain schema/migration fingerprints, auto-increment positions, and all supported application table rows in foreign-key order. PDO uses an unbuffered repeatable-read snapshot; schema changes must stop during capture. The format is deliberately limited to the current InnoDB schema: views, triggers, routines, events and unknown tables are rejected. A record exceeding 8 MiB fails the backup. No plaintext dump or credentials are written to process arguments. Recovery requires the same schema, migrated into an empty isolated database with a different name. It does not execute SQL supplied by an archive, disable foreign keys or drop existing records to make room.

Operators provision three nonoverlapping locations outside the application tree: a backup directory, an independent durable deletion-state directory and a key directory. Directories require mode 0700; files require 0600, current service UID ownership and no symlink/hardlink alias. POSIX atomic rename, fsync and flock must work reliably on the actual shared durable filesystem. These checks do not establish physical independence, ACL safety, off-host durability, storage encryption, administrator trust or service-level guarantees.

The authenticated external state contains a random ledger identity, monotonic revision, backup registry, one active installation generation and minimal deletion UUID/status records. It is atomically replaced and synchronized under an exclusive lock. Accounts gain random immutable recovery UUIDs, preventing numeric-ID reuse from targeting a different account. The external file is outside the restorable database and must never be rolled back with it. A correctly authenticated but stale copy of the whole external state cannot always be detected from an older database snapshot; independent freshness/durability evidence is an explicit production prerequisite. Missing/corrupt state, missing registered backups, newer required revisions and uncertain deletion outcomes fail closed. Neither an HMAC nor a green local test proves external freshness.

## Deletion and concurrency

When enabled, deletion acquires the external lock before the existing owner-lock transaction, rechecks installation admission and the password/session/owner rules, and uses the existing graph cleanup. Before committing, it synchronously records `pending`. Capture failure rolls back the database. After commit it records `committed`; failure at that point preserves the successful live deletion, signs the user out, logs only a fixed operational message and leaves recovery blocked by the pending record. An uncertain commit is never silently interpreted as success or rollback.

`resolve-pending` requires explicit confirmation of the authoritative original database and its active installation generation. Under the same external lock it checks each UUID under a database lock: present means rollback/cancelled; absent means committed. A restored copy cannot resolve this ambiguity. If the original is lost and commit outcome cannot be established independently, recovery remains blocked; do not initialize a replacement ledger or guess. Records are retained without automatic pruning because every restorable copy must remain covered.

Backup, purge, deletion and recovery serialize their state changes with one external lock; contention fails safely rather than waiting indefinitely. Normal HTTP admission reads the atomically published authenticated state without taking that long-lived lock. Operators must drain already authorized requests, workers and writers during cutover. Every process must use the same durable state and key. Multiple independent volumes or unreliable network filesystem locks are unsupported.

## Recovery and retention

`RECOVERY_MODE=recovery` blocks application HTTP before sessions/authentication; `/up` stays liveness-only. Operators must additionally isolate the database, static/private files, mail and all background processes at the platform boundary. Commands require explicit isolated-target confirmation. Import authenticates the entire archive before writing and streams it again inside a transaction. An `importing` marker remains blocked on failure; only a completed import and reconciliation becomes `reconciled`. Failure requires inspection and a newly empty isolated target, not automatic deletion of its contents.

Reconciliation applies committed suppression records using the same child-first ownership checks as live deletion. It clears all restored sessions, reset tokens, pending email links, revocation rows and remembered sign-ins, including surviving accounts' pre-recovery authentication. Admission rechecks the current external state and reapplies reconciliation while locked. Publishing a new active generation invalidates the original installation. Recovery mode continues blocking HTTP until the operator switches the verified target to live and performs controlled cutover. Failed admission remains closed.

Managed artifacts expire after 29 days, leaving one day of operational margin before the approved maximum of 30 days. Laravel schedules purge every minute when live. Purge considers only UUIDs registered by this workflow, validates file boundaries and never enrolls historical files by scanning a directory. Partial/failed artifacts also expire. Schedule execution, timely alerts, off-host/copy lifecycle, clock correctness and storage-appropriate disposal are operator responsibilities; stopping a scheduler cannot be solved by application code. Backup frequency/RPO/RTO remain unapproved and must be assigned before production use.

## Limits

No production store, key custody, scheduler, alert delivery or ingress isolation is provisioned by this change. Existing plaintext and historical encrypted artifacts are unchanged and cannot be restored by these commands. The expired SQL export requires separately authorized containment/disposal. Legacy backups without recovery UUIDs and independent deletion history cannot be made safe by fabricating records now. Whole-host snapshots that include and rewind the ledger defeat its independence and are prohibited. Master-key rotation and ledger compaction require a separately reviewed procedure covering all remaining backups; neither happens automatically.

The required UUID column makes older user-creation code incompatible, and older account-deletion code cannot maintain this ledger. Once enabled, rollback must retain recovery-aware code/schema or keep all writers stopped for compatible forward repair. Dropping the migration or deploying a pre-remediation release is not a safe routine rollback while managed backups remain restorable.
