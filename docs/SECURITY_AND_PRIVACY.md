# Security and privacy

Use Laravel session authentication, password hashing, CSRF middleware, validation, output escaping, and authenticated route middleware without weakening defaults. Authorize ownership and visibility server-side via Policies/Gates; hidden controls are never sufficient.

New habits default private. Journals, mood, and habit notes are private. Private-account follower requests require approval. Public/follower-visible activity never exposes private notes. Avoid logging passwords, tokens, journal content, mood, or private notes.

Keep secrets only in ignored environment files and document variable names—not real credentials—in `.env.example`. Use a distinct testing database, validate its name before destructive migrations, and never point tests at the development database. Permanent deletion later requires explicit confirmation and complete related-data removal.

Phase 3 daily routes, history, and Livewire mutations remain owner-only for every stored habit visibility. Notes and N/A reasons are private, hidden in model serialization, and excluded from summary queries. Server-owned IDs and revisions are locked in components and revalidated in transactional Actions; neither hidden buttons nor optimistic tokens grant access. Trashed habits cannot be queried through tracking routes. Recording/configuration/lifecycle writes share the same user-then-habit lock order.

Phase 4 analytics remains owner-only for all visibility/account preferences. The embedded Livewire heatmap authenticates and authorizes on every render/action, locks its habit identity, and validates year/date/page inputs. Query scopes and existing Habit policies exclude foreign/trashed records. Analytics projects no notes or N/A reasons into queries, results, HTML, or hydration state. It performs nonlocking, consistent reads without modifying raw data or introducing public routes.

Phase 5 journal reads/writes require authentication and an owner policy regardless of account privacy. The Livewire editor locks owner/date/entry/revision/timezone state and rejects a hydrated snapshot if the session user changed. Every Action rechecks owner-scoped state, current timezone, and date under a transaction. Expected entry ID plus revision detects deleted/recreated rows. Confirmation is required before the editor calls deletion; the deletion Action always enforces ownership and concurrency independently.

Content and mood are hidden from general model serialization, absent from unrelated views/analytics, and never placed in URLs or browser storage. Only the authorized editor includes those fields in HTML/Livewire state. Save Actions turn database failures into generic validation feedback without logging SQL text/bindings or chaining the private exception. Session/CSRF middleware remains unchanged. Physical journal deletion has no application recovery and does not enable permanent habit deletion.

Phase 6 adds authenticated shared reads, extending Phase 4's owner-only presentation through distinct `viewShared` abilities. Existing management, tracking, journal, category, and mutation permissions remain owner-only. Private accounts gate even public-marked habits behind accepted following; pending/reverse-direction follows grant no follower access. Follow transitions authorize the actual actor and compare current row identity/state under ordered user locks. Confirmation state is locked for unfollow/removal; hidden controls are never the authorization boundary.

Shared profiles project explicit fields: username/display name (fallback username), privacy and the viewer's relationship state; bio/theme/accepted counts and permitted activity require the account gate. No email, registration-name fallback, other users' requests, private habit contribution, notes/reasons, journal/mood, category metadata beyond the associated label, or pending setup is shared. Shared analytics filter membership before counts/denominators/streaks, use the subject timezone, and omit editor links from the payload itself.

People pages, nested heatmaps, and profile settings pin the session user and reject snapshots reused by another account. Fresh requests reauthorize privacy/follow/visibility state. In-flight reports retain a consistent authorized snapshot; already delivered data cannot be recalled. Existing explicit sharing preferences apply to stored history when Phase 6 is enabled; private defaults remain intact. See [ADR-0006](adr/ADR-0006-SHARED-PROFILE-ACCESS.md).

Phase 7 extends session identity pinning to the older category, habit and tracking pages through `RequiresSameUser`. A snapshot from a prior account is rejected before hydration can reuse its private draft or save it under the new account. Existing ownership policies still authorize each record/action independently.

Web responses set private/no-store caching, no-referrer, nosniff and SAMEORIGIN framing headers. Registration, reset-link and reset-submission POSTs are independently limited to 20 requests/minute per route/IP; login retains its existing five attempts/minute per normalized login/IP and reset delivery retains the broker's per-account cooldown. Normal Livewire updates are not globally throttled. Trusted proxy configuration determines the real client IP and must be verified on the deployment host.

Unhandled database errors are logged as ERROR metadata with exception class, SQLSTATE and application operation. Their SQL, bindings, driver message, exception object and argument-bearing stack trace are omitted because they can contain private text or credentials. Production debug must remain disabled. This changes diagnostic detail, not transaction rollback or authorization behavior.

The browser harness uses only synthetic data, an explicitly opted-in/guarded test database and normal middleware. A process lock prevents overlap with PHPUnit resets. Test reset mail is captured in ignored local logs; those logs, tokens and authenticated storage are never CI artifacts. See [deployment and recovery](DEPLOYMENT.md) for production secrets, cache/proxy/TLS and backup requirements.

Authentication security fixes: password reset invalidates the user's database sessions and rotates remember credentials. Laravel's session-authentication middleware also verifies the stored password hash on web and Livewire requests, rejecting stale sessions before protected reads/writes. Failed validation does not revoke sessions. Requests already authorized before a reset cannot be recalled; subsequent requests must reauthenticate. No session-management UI is introduced.

Password confirmation requires authentication and CSRF, validates a string password, and limits submissions to five per minute per user across IPs. Fortify retains its confirmation lifetime and intended destination. Reset-link responses use the same status/message for known, unknown and per-account-throttled addresses in HTML and JSON. Invalid reset tokens and unknown reset emails also share a failure response. Existing validation and IP-based public-auth throttles remain, as does the broker's minimum timebox; actual synchronous mail latency can exceed that minimum. Operational mail exceptions are not hidden. Registration's duplicate-email validation is unchanged.

Authenticated password changes use Fortify's authenticated PUT route, CSRF, five attempts/minute per user across sessions/IPs, current-password verification against an exclusively locked fresh user, and the existing environment-specific password policy. Bcrypt input beyond 72 bytes and NUL characters are rejected at the update boundary; literal hash-looking input is hashed rather than accepted as a stored hash. A stale admitted hash is rejected even if the raw password has not changed. Only password, remember token, and user update timestamp change; profile/privacy and all activity remain unchanged. Reset tokens and other database sessions are revoked transactionally; session-authentication middleware rejects stale authenticated payloads written after revocation. The initiating session rotates its ID/CSRF token and loses any previous password-confirmation timestamp and persistent remember cookie. Passwords are never flashed or placed in Livewire snapshots. Password reset also locks and rechecks the token so an admitted stale reset cannot overwrite a newer change. Already-authorized requests cannot be recalled; subsequent requests must reauthenticate. Database sessions and reset tokens must remain on the same connection for atomic cleanup.

Confirmed account deletion requires authentication, CSRF, a five-per-minute account-bound limit, current password and explicit acknowledgment. A submitted account ID only rejects stale forms; it never selects the account to delete. Fresh credentials, remembered admission and session revocation are rechecked under the user lock. The owner's live graph and authentication state are deleted atomically, while foreign records remain. Sign-out happens only after commit. Recovery/login/session writers reject missing users; database errors are generic and do not expose content. Cross-owner reference inconsistencies abort cleanup. External deletion reconciliation before live backup restore is mandatory and remains unverified; see [ADR-0011](adr/ADR-0011-ACCOUNT-DELETION.md).
