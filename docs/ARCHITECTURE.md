# Architecture

habit.log is a Laravel modular monolith. Docker Compose provides Apache/PHP, Vite and MySQL for local development; a separate production image packages the runtime with compiled assets. Native Ubuntu/WSL development remains supported by starting only the MySQL service. [ADR-0007](adr/ADR-0007-CONTAINER-RUNTIME.md) supersedes the initial native-only runtime decision; [the Docker guide](DOCKER.md) describes configuration, persistence and verification.

Livewire components own UI state and interaction, with Alpine.js for small client-side behavior. Blade renders views but does not contain substantial business logic. Validation occurs at Laravel/Livewire boundaries. Policies/Gates and authentication middleware enforce authorization server-side.

The daily dashboard adds a computed, read-only today projection in its Livewire page. It reuses `TrackingDate` for eligibility/effective setup, reads only owner habits in batches of 100 within a consistent transaction, keeps six preview rows, and counts all eligible/logged habits. Entries project only status/value and checkpoint counts; notes and reasons are omitted. `RequiresSameUser` protects hydrated requests. Analytics still runs through the existing independently authorized `ActivityHeatmap` component and unchanged analytics services; a Blade summary component separates statistic presentation from the shared calendar. For null consistency results, the Livewire renderer maps existing report counters to contextual copy. Owner-dashboard-only existence reads include trashed habits when distinguishing new accounts and first check-ins; they select no private activity content and never run for shared views. This presentation metadata does not alter the analytics report or write data.

Habit configuration embeds the existing Categories Livewire component in a locked inline presentation mode. Both entry points use the same validation, recommendations, ownership checks, and duplicate handling. Inline selection emits a category ID instead of redirecting; the parent scopes and authorizes that ID again, updates only its unsaved form state, and closes the dialog. Creating a category remains a separate explicit write. No draft is stored in session, local storage, or history, and no new endpoint or persistence layer is introduced.

Use controllers/components, Eloquent models, form validation, and policies before adding layers. Extract an Action/Service only for reusable, transactional, complex, or independently testable work—not every CRUD operation. Use database transactions for multi-record state changes.

MySQL uses foreign keys and indexes driven by real queries. Migrations should be reversible where practical. Activity source records remain authoritative; normalized heatmaps and analytics are derived until profiling justifies a cache, with explicit invalidation rules.

Phase 3 uses transactional habit/entry Actions for configuration versions, cancellation, lifecycle intervals, and recording. `TrackingDate` is shared eligibility/version resolution used by policies, pages, and saving. `HabitEntryForm` supplies boundary validation reused by the entry Action. Reads remain scoped Eloquent queries; daily summaries eager-load only the relevant date's latest setup and entry. The daily overview additionally projects checkpoint snapshot counts and a computed presentation summary explicitly limited to the current 20-row page; an owner-scoped existence read including Trash distinguishes onboarding from restoration. It keeps eligibility in `TrackingDate`, adds no scoring, and leaves recording Actions and the entry editor unchanged. No repository, event-sourcing system, analytics cache, or API layer is added. See [ADR-0004](adr/ADR-0004-DAILY-TRACKING-HISTORY.md) for calendar/history semantics.

Phase 4 derives analytics through `HabitScore`, `ActivityAnalytics`, and `StreakCalculator` under `app/Services/Analytics`. The owner-only `ActivityHeatmap` Livewire component is reused on the dashboard and habit detail page. Blade renders prepared results; Alpine handles calendar focus and details. Reports use a single MySQL repeatable-read transaction with nonlocking reads, including owner timezone, configuration, entries, and checkpoint completions. A two-connection regression verifies that a concurrent committed edit cannot mix old parent and new child values.

History is processed in 50-habit and 500-entry batches. Configuration/suspension boundaries and entry overrides form date segments; absent days are not individually materialized across lifetime history. All history is read for lifetime streaks; only the selected year's daily cells and selected-year entry details are retained for rendering. The same segments calculate trailing/calendar-year consistency and profile daily means. No cache, new dependency, repository, queue, or analytics schema is introduced.

Phase 5 uses `Journal`, `JournalPolicy`, `JournalForm`, and transactional `SaveJournal`/`DeleteJournal` Actions. The date-based Livewire editor lives at `/journal?date=YYYY-MM-DD`; ownership comes from the session. An exclusive user lock followed by an owner/date row lock serializes absent-row creation and stabilizes timezone. ID/revision checks detect concurrent edits and deletion/recreation. Transactions remain short and take no habit locks. Journal validation is independent of habit eligibility/version logic. Database save failures become safe field feedback without reporting SQL bindings containing private text. Journals are not analytics inputs and introduce no package, repository, queue, or cache.

`resources/js/app.js` tracks a numeric browser-history position so a cancelled journal, activity, or habit-configuration Back/Forward action returns to the original entry before Livewire processes `popstate`. It stores no draft content; ordinary Livewire navigation and native unload checks cover the other paths. Browser regressions verify both cancelled and accepted traversal.

Phase 6 adds directional `Follow` records and `FollowUser`/`TransitionFollow` Actions. Mutations lock both user rows in ascending ID order, then the follow row; profile saves lock their own user row through `SaveProfile`. Expected relationship ID and state reject stale approvals/removals. No automatic pending-request conversion runs on privacy changes. `InteractsWithFollows` reuses authenticated actor checks and confirmation state across People pages.

`SocialAccess` supplies the account gate and filtered habit query used by shared policies, profile lists, and analytics. `UserPolicy::viewShared` and `HabitPolicy::viewShared` authorize shared reads separately from existing owner management abilities. `ActivityAnalytics::reportForViewer` accepts explicit viewer and subject identities, filters before aggregation, and reuses the existing engine within a consistent nonlocking transaction. Shared results omit private editor URLs. `ActivityHeatmap` pins its viewer, optional subject, and habit IDs and reauthorizes every request. No report array or authorization decision is persisted across requests.

The `/people` pages use computed server-side projections and paginated lists; they do not hydrate full User models into browser state. Read-only habit metadata uses the current effective tracking version, excluding pending setup. See [ADR-0006](adr/ADR-0006-SHARED-PROFILE-ACCESS.md) for the disclosure and revocation contract.

Shared profile refreshes and relationship mutations increment a locked presentation revision to remount the nested report with fresh authorization. Successful shared heatmap interactions notify the parent to refresh its metadata/list without resetting the selected day; that parent refresh does not emit another report update. Shared habit details also provide an explicit refresh. A revoked Livewire action redirects with Livewire navigation to the freshly authorized profile (or People when the username no longer exists), omitting report HTML, instead of leaving stale content behind an error overlay. Direct denied URLs remain 404; authentication/session failures retain their rejection statuses. These are request-time refreshes, not polling, push notifications, or persisted authorization caches.

Phase 7 uses `RequiresSameUser` for the older owner-page session boundary and a small web middleware for sensitive-response headers and narrowly scoped public-auth throttling. The exception report callback projects safe database-failure metadata instead of logging SQL/bindings. Neither control replaces record policies or transactions.

Analytics prepares immutable SQL DATE/configuration fields once per existing history batch, avoiding repeated date casts for every entry. This is request-local preparation within the same consistent read, not a persisted report or authorization cache. Raw activity, formulas, batching and visibility filtering remain unchanged. The history-position navigation guard now covers activity drafts as well as journals, storing only a numeric history position.

Entry history prepares a single 20-entry page under a nonlocking repeatable-read transaction. The authenticated owner's habit is authorized on every render; entries additionally match that owner, and version relations are restricted to the same habit. Projected entry/version/checkpoint fields exclude notes, N/A reasons and checkpoint labels. Batched eager loads validate immutable checkpoint membership; `HabitScore` calculates normalized performance and `TrackingDate` supplies eligibility/read-only context. No lifetime analytics report, per-row database lookup, new schema, or persisted cache is introduced. A two-connection regression verifies that an edit committed between entry and checkpoint reads cannot mix versions of the saved outcome.

Authentication recovery uses Fortify response contracts for uniform reset-link feedback (known, unknown and recently requested addresses) and uniform invalid-user/invalid-token failures. The broker still performs validation, timeboxing, token creation and mail delivery; delivery exceptions are not swallowed. `AuthenticateSession` runs in the web group, including Livewire updates, so a saved password-hash mismatch rejects a session before component hydration. ResetUserPassword updates the password/remember token and removes the user's database sessions in a transaction on the current default connection. Explicit deletion covers legacy sessions without a hash marker; the middleware covers stale sessions written back by an in-flight request. The configured production/local session store is the database; changing stores or moving sessions to a separate connection requires revisiting legacy-session revocation and transaction guarantees. Password confirmation uses Fortify's intended redirect/timestamp flow, a bound view, string validation and a five-per-minute user-based limit.

Account management Phase 1 enables Fortify's password-update contract and adds a native Blade Security form at `/settings/security`. `UpdateUserPassword` derives ownership from the guard, validates with the existing password policy, locks the fresh user, checks both the admitted credential hash and current password, and calls the shared `ReplacePassword` action. That action hashes literal input, rotates remembered credentials, consumes reset tokens, and removes other database sessions inside the caller's transaction. `ResetUserPassword` now takes the same owner lock and rechecks its token after locking before using the shared action. The update response retains the initiating session with the committed hash marker, destroys its old ID, regenerates CSRF state, clears its remember cookie and old confirmation timestamp, then redirects. Fortify's subsequent token cleanup remains harmless and its standard events are preserved. No new schema, dependency, email-change state, or session-management UI is introduced. See [ADR-0008](adr/ADR-0008-AUTHENTICATED-PASSWORD-CHANGE.md).


Account management Phase 2 uses a native Settings `EmailChangeController`, transactional `EmailChanges` action, `PendingEmailChange` model and Laravel notifications. The HTTP boundary verifies signed links and CSRF/authentication; the action derives/rechecks the owner and admitted credential state under user-then-request locks. No mail is sent while database locks are held. Request/resend availability is private; uniqueness is enforced only on verified confirmation. `FinalizeCredentialSession` shares the existing password response's session rotation with email confirmation. `ReplacePassword` rehashes the same password on email confirmation and cancels pending changes for both password flows.

`AccountPasswordBrokerManager` retains Laravel's broker with a small database token-repository extension. Token creation/deletion rechecks the fresh user identity/hash under its lock so a late recovery operation cannot act on an email that has been reassigned. Reset submission also rechecks the email under the existing lock. This relies on the current default-connection database session/reset stores. Signed tokens remain outside model serialization, flashed input and production application/access logs; the existing Apache format omits query strings. See [ADR-0009](adr/ADR-0009-VERIFIED-EMAIL-CHANGE.md) and [the email-change report](ACCOUNT_EMAIL_CHANGE_REPORT.md).

Account management Phase 3 uses `ManageSessions` and a native `SessionController` submission to list and revoke owner sessions in Security Settings. `RejectRevokedSession` runs before session-authentication middleware, and `RevocableDatabaseSessionHandler` extends Laravel's database handler to serialize authenticated writes with revocation. Login events stamp the credential marker and recheck admitted credentials under the user lock. Stable hashed origins and durable revocation rows cover stale payload/ID regeneration; bulk and credential changes retain password-hash invalidation. Listing selects metadata only and projects opaque UUID selectors plus conservative device descriptions. No session payload decoding or IP disclosure occurs. This requires the canonical database session table on the default connection; unsupported configurations disable management. [ADR-0010](adr/ADR-0010-SESSION-MANAGEMENT.md) records the remembered-sign-in tradeoff and rollback limitations.
