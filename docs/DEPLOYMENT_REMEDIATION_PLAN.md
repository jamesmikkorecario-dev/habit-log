### Target configuration and migration checklist

- Record deployment operator, release revision/image digest, domain, ingress/proxy chain, database and persistent-volume ownership. Use `public/` as the document root and keep the DB private.
- Verify production environment and debug disabled, a stable securely recoverable application key, HTTPS application URL, canonical-host enforcement and Secure/HttpOnly/SameSite cookie settings through the actual proxy. Check no-store on private HTML and Livewire responses through the CDN/cache.
- Use the supported database session driver/table on the same canonical connection as account operations and reset tokens. Exercise individual/bulk session revocation, late writes and confirmed account deletion on synthetic accounts in an authorized staging environment.
- Explicitly select file cache and synchronous work, or implement and verify an approved alternative. The default database cache/queue tables are absent; no current business feature needs a worker. No current application business job needs a scheduler. Backup purge still needs its own approved automated mechanism and owner.
- Configure a real security-mail transport, sender authentication, delivery/failure monitoring and secret storage. Verify mailbox receipt and links through the real host. Check the production password-policy compromised-password lookup and its failure behavior.
- Verify writable restricted storage/cache paths and persistence across replacement containers, cached configuration/routes/views, health checks and restarts. `/up` is liveness and does not establish DB/mail/recovery readiness. No Vite/dev server, debug tooling or test account belongs in production.
- Inspect migration status and existing schema; stop writers at the backup/upgrade boundary. Use the documented production commands, never `migrate:fresh`, `composer setup` or generic development seeding. Test a representative populated upgrade in isolation and preserve the backup/release/key recovery boundary.
- Record rollback triggers and compatible-code/forward-repair steps. Schema `down()` operations for history/journal/follow data can be destructive; green rollback tests do not make production rollback data-preserving. Reconciliation remains mandatory if rollback uses a backup.

### Manual and external-service journey checklist

Use authorized synthetic accounts and safe staging mailboxes. Record environment/version, expected result, actual result and evidence for each journey:

1. Register, sign in, reset/change password, verify an email change and revoke another session; test missing, invalid and expired input/links and delivery failure without account enumeration or logged secrets.
2. Edit Settings; cancel and confirm leaving, navigate Back/Forward, trigger validation/network failure, and verify logout/revocation/deletion takes precedence over draft protection.
3. Create all five habit types, review a category, record/edit N/A and numeric zero, navigate historical dates and midnight/timezone boundaries, archive/trash/restore, and inspect entry history and analytics. Preserve the approved heatmap, its keyboard/date alternatives and neutral/scoring semantics.
4. Save/delete a private journal, follow a private account, approve/cancel/revoke access, and verify hidden activity/notes/mood/journals never appear for an unauthorized viewer, including an already-open page after its next request.
5. Complete and cancel account deletion; verify foreign accounts remain usable and deleted credentials, sessions and links fail. Restore protection requires the separate isolated reconciliation drill above.
6. Repeat key tasks at 1440px and 390px with keyboard only and NVDA or VoiceOver, then physical mobile touch/virtual keyboard, supported Firefox/WebKit and native 400% zoom. Check labels, live status/error announcements, focus order/return, dialogs, navigation, contrast/forced colors, date controls and long content. Record browser-controlled unload limits accurately.
